# 文件排序修复与验收

## 根因

1. OSS 与 S3 普通 Bucket 的列表按对象 key 正序分页。原实现仅对首屏及已经加载的对象做本地排序，因此最新文件位于后续页时，选择“时间最新”也无法把它排到当前首屏。名称倒序存在同样的问题。
2. 原上传成功刷新依赖 `BrowserScreen` 观察历史成功 ID；重新进入页面也可能因历史 ID 刷新，而上传时切换目录或页面不活跃又不能可靠失效真实上传目录的缓存。
3. 旧列表请求可能在上传完成、缓存失效之后才返回，再把上传前的目录数据写回缓存。排序比较器本身无法修复这种旧快照覆盖。
4. LazyColumn 的稳定 key 会保留旧的首个可见对象作为滚动锚点。即便数据已经重排，用户仍可能停留在原对象附近，视觉上像“排序没生效”。
5. 大小写不敏感同名且修改时间相同的文件缺少确定的比较结果，输入顺序变化时可能换位。

## 修复行为

- 名称正序保持原按需分页，不为了首屏展示扫描完整目录。
- 时间正序、时间倒序和名称倒序先读取完整当前目录的元数据，再一次性发布全局排序结果；只读取当前层，不递归进入子目录，不读取文件内容。
- 完整排序每次请求最多 1000 条，扫描最多 10000 条。读满 10000 条且仍有下一页时立即停止，不再读取额外页面；恰好 10000 条且已到末页则正常完成。超过上限、重复分页令牌或空页仍宣称有下一页时，显示明确错误，不把局部排序伪装成完成；可切回名称正序继续浏览。
- 完整排序不复用带 `nextMarker` 的部分缓存；已经完整加载的目录可以直接重排，无需为了切换方向再次请求。
- 设置变化通过 ViewModel 的排序观察统一生效；加载中的旧目录、旧排序和旧刷新代次不会继续扫描或覆盖当前结果。切换排序时列表回到顶部，避免稳定 key 的旧滚动锚点遮住新的首项。
- 上传服务先使提交时的账号、Bucket 和目录缓存失效，再发布成功。ViewModel 只对新成功且属于当前目录的任务刷新；切到其他目录不触发无关请求，回到上传目录时缓存已失效。
- 目录缓存增加进程内失效代次，拒绝失效之前发起、失效之后才返回的旧响应；当前页和追加分页都进行核对。
- 文件夹优先策略保持原样。按时间最新时，新上传文件应在文件组内根据服务端修改时间排序，不会强行排在文件夹前面；按名称排序时不会强制把新上传文件置顶。
- 同时间、大小写不敏感同名文件再以完整 key 确定次序，防止缓存恢复或分页输入顺序变化导致随机换位。

当前项目没有大小排序选项，本次不额外新增。

## 本地回归

```bash
bash gradlew :app:testDebugUnitTest \
  --tests '*ObjectDirectoryLoaderTest' \
  --tests '*OssObjectSortTest' \
  --tests '*OssListCacheTest' --console=plain
git diff --check
```

测试包括：最新文件位于第二页、名称倒序跨页、名称正序保留分页、目录超过 10000 条、过期代次停止扫描、分页令牌循环、同时间同名稳定排序、上传后旧请求不能重新写回缓存、全量清缓存拒绝旧请求、目录失效不污染其他账号、磁盘缓存恢复时间戳精度。

这些测试全部使用本地 fake 元数据与临时缓存；未访问真实 OSS/S3 目录或文件，未进行真实上传。S3 文件操作仍受用户明确禁止，不得为了验收本修复而擅自执行。

## 验收边界

完整时间排序需要比名称正序多请求当前目录元数据，数据量较大时会保持加载状态，直到完整获取或明确失败。它不提供跨多个远端请求的一致性快照；外部客户端同时修改目录时仍受供应方分页与一致性语义约束。本应用自身的上传通过缓存失效代次避免旧结果覆盖。

在另行获得真实文件测试授权后，可用“最新文件的名称按 key 正序排在后页”的目录验证首次进入、切换排序、缓存重入、当前目录上传以及切走后上传完成再返回。没有授权时继续使用本地模拟数据，不能以本地通过宣称真实文件排序已验收。
