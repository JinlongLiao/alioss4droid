# 上传持久化性能修复与验收

## 已修复的问题

- 上传历史首次读取从仓库构造器移到 IO；页面显示“正在加载上传历史”，命令和历史清理必须等待初始化完成，不把初始空值解释成历史丢失。
- 页面发起上传或取消时先启动前台服务，再由服务的单消费者 IO 命令队列处理持久化。主线程只管理 Job、计数和通知，不获取历史写锁，不执行 JSON 编码或 fsync。
- 上传开始、已确认成功、失败及取消收尾均等待 IO 提交完成后才发布状态。整个收尾使用不可取消上下文，避免 IO 返回时的取消跳过 Job 移除。
- 服务销毁后停止接受命令，已经接收的命令继续落盘为中断，不再启动网络上传。停止服务时使用系统启动代次，避免把尚未处理的新命令一起停止。
- 清理历史先逐项清理文件，汇总成功 ID 后只对最新历史提交一次，避免原逐条重写全历史的平方级序列化/落盘。清理保留锁一直持有到提交结束；失败保留记录，迟到的历史重试不能重新插入已清理任务。
- 初始化历史成功 ID 在 IO 中固定。ViewModel 等待初始化后使用该固定集合，避免把首批历史或初始化期间极快新完成任务混淆。
- 多选文件时 ViewModel 不在 Main 查询文档名称，先启动前台服务；每个任务独立在 IO 查询名称并完整保存，再构造远端 key。慢云文档查询不占用串行命令消费者，取消通过 `CancellationSignal` 通知提供方。提供方忽略取消信号时，读取线程仍需等待提供方退出，不能保证强制终止外部代码。
- 排队转运行必须原子校验同代次且仍为 QUEUED；名称保存必须同代次、仍为 RUNNING 且待解析。已保存 CANCELLING 不会被迟到开始或名称解析撤销。SDK 已确认成功后仍不可取消地保存成功结果。
- 新任务显式保存 `resolveDisplayName=true`，解析成功并提交后才清除；提供方或名称保存失败保留标记供重试。旧 JSON 缺少该字段时默认 false，沿用已保存对象名称，不因重试改变 key。

## 进度 journal 与持久化保证

完整历史仍保存在原 `upload_tasks.json`，JSON 列表格式和旧 AtomicFile 备份读取保持兼容。只有同一 RUNNING 任务的字节数改变时，原子保存该任务的小型 `upload_progress/<id>.json`，不再每个百分比重新序列化全部历史。

每次入队或重试生成新的 `attemptId`。journal 同时绑定执行代次和主快照摘要，恢复只接纳同 ID、同代次、同目标、主快照仍为 RUNNING 且摘要匹配的进度；随后才将进程中断任务变为 INTERRUPTED。旧 journal 不能覆盖终态、新排队、新重试，也不能覆盖同次执行内重新提交的主快照基线。

队列、取消和终态仍完整提交历史。提交明确等待 `FileDescriptor.sync()`，然后同目录原子替换；任何失败都向调用者抛出，仓库不提前发布未保存状态。完整历史成功后才清理已吸收的 journal，即使旧 journal 删除失败，恢复的代次和摘要判断也不会复活旧状态。`.commit` 半写文件从不参与恢复。

运行期的迟到旧代次进度和终态同样被仓库入口拒绝，不仅依赖磁盘恢复过滤。服务重试等待旧 Job 完全收尾后才进入新代次。

回退到不知道 journal 的旧代码时，完整历史和终态仍可读取，但未结束任务最近一次完整快照之后的百分比可能较旧；不应把旧版本缺少 journal 支持误当作新版本持久化失效。
